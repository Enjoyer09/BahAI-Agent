## Prod error "AI provider-lər hazırda cavab qaytarmadı" — diagnosis + fix
User reported the generic provider-failure toast. Investigated `backend/chat/runner.js`.

### Root cause
- The generic message (runner.js ~L451) is shown ONLY when
  `isGenericFailoverCandidate(providerCandidates)` == true, i.e. `length > 1`.
  It's the DEFAULT `userMsg` used for ANY status NOT in {401,429,402,503,404,
  network}. So a **500/502 from the gateway** (the most common case) lands here.
- For `web_chat` "auto" with OmniRoute enabled, the failover pool is
  `omniRouteFallbackModels` (auto, gpt-5.5, claude-sonnet-4.5) — ALL routed
  through the **same** OmniRoute base URL. `buildOpenRouterFallbackCandidates`
  / `buildNvidiaProviders` only add a real second upstream IF
  `OPENROUTER_API_KEY` / `NVIDIA_API_KEY` is set (dev .env has neither).
- => "alternative models" are NOT alternative providers. A single gateway
  outage/5xx makes every candidate fail identically → generic toast. This is a
  **single point of failure**, not a real multi-provider failover.
- Also: each candidate was tried exactly once; a transient 5xx immediately
  burned the whole pool (no per-candidate retry).

### Fixes implemented (backend/chat/runner.js)
- Added `callCreateStream()` — retries a single candidate ONCE (350ms backoff)
  on transient 5xx/429/network errors only; excludes AbortError (deadline) and
  deterministic 4xx. Absorbs gateway blips without needing a second provider.
- Honest message: detects when all candidates share one base URL and appends a
  hint that backups (OpenRouter/NVIDIA) aren't configured. Keeps "AI provider"
  substring so existing tests pass.
- Tests: added 2 cases (transient-5xx single-candidate retry; single-gateway
  hint). Runner suite now **26/26 pass** (was 24).

### Minimization plan (priority order)
1. **Configure a REAL second provider** (highest impact): set `OPENROUTER_API_KEY`
   (or `NVIDIA_API_KEY`) in the live env — `resolveWebAutoPlan` already appends
   those as separate failover candidates with a different base URL. This makes
   failover cross-provider, not same-gateway.
2. Keep `AUTO_SMART_MODEL` a general model in live env (P1 caveat) — prevents
   conversational-tier 400s from a coder model.
3. Confirm live `OMNIROUTE_BASE_URL` is the production gateway, not the dev
   `https://api.freemodel.dev/v1` free proxy (rate-limited/flaky).
4. Observability: enable `BAHAI_DEBUG_EVENTS=1` in staging to capture the real
   upstream status behind the generic toast; aggregate `provider_failure`
   telemetry to confirm OmniRoute is the culprit.
5. TTFT cap is 8s for web text (LLM_FIRST_TOKEN_MS). If the gateway is just
   slow (not down), raise `LLM_FIRST_TOKEN_MS` to avoid false failover — but the
   user's message is the non-timeout generic one, so this is secondary.
6. (Optional, future) client-side auto-retry on this specific error before
   showing the toast, to mask transient blips for users.

## Image/vision attachment bug — "agent returns irrelevant answer for a picture"
User reported: when he gives the agent a motherboard photo, it immediately returns
an off-topic/irrelevant (aidiyyatsiz) reply. No image was re-shared in chat, so this
was investigated as a CODE bug (not vision-reasoning on the actual photo).

### Full trace (verified file by file)
1. **Frontend capture OK.** `Composer.tsx fileToAttachment` reads the file as a
   `data:image/...` URL, sets `type:'image'`, `mimeType`. `chatService.ts
   buildPreparedMessages` preserves `url` into the payload (line 307-315);
   `sanitizeWebChatHistory` does NOT strip attachments. So the image data URL
   reaches the backend intact.
2. **Routing detects vision OK.** `routes/chat.js` `hasImageAttachment` (type==='image')
   → `webTaskType='vision'` → `buildProviderCandidates(primaryTask='vision')`. NVIDIA
   vision candidates are PREPENDED (`[...nvidiaCandidates, ...cloudCandidates]`).
3. **Image is built into the payload OK.** `helpers.js normalizeMessagesForModel`
   keeps `image_url` parts (requires `attachment.url.startsWith('data:image/')` — true).
   So the model genuinely RECEIVES the pixels. The image is NOT lost in transit.
4. **THE BUG — model selection can pick a text-only model.**
   `providers.js` (315-318): if `useOmniRoute` is true AND `WEB_CHAT_VISION_MODEL`
   is NOT set, `orderedModels = omniRouteFallbackModels` (the gateway "auto" chain).
   The OmniRoute gateway then resolves the vision request itself and CAN pick a
   plain text-only model. That model cannot see `image_url`, so it answers from the
   OCR/text hints → an "irrelevant" reply. (This exact failure is documented in the
   code comment at providers.js:306-313.) The NVIDIA `nemotron-3-nano-omni` vision
   candidate is prepended only if `NVIDIA_API_KEY` is set; if it fails, failover falls
   back to the same gateway auto path.
5. **Dead safety net.** `BaseProvider.formatAttachments` is meant to strip attachments
   for providers without `image_vision`, but it is NEVER CALLED anywhere (grep:
   definition only). So there is no guard that detects "chosen model can't see
   images" and reroutes — the image is silently sent to an incapable model.
6. `runner.js adaptMessagesForProvider` only rewrites `image_url`→`<img>` for the
   LEGACY `llama-3.2-11b-vision` model; the default nemotron-omni uses standard
   `image_url`, which is fine IF the model is actually multimodal.

### Root cause (plain): the photo IS sent to the AI, but the request can be handed
to a "blind" text model that can't read pictures, so it replies off-topic.

### Fix (operator action, no code change required)
- Set `WEB_CHAT_VISION_MODEL` in the live Railway env to a vision-capable model id
  the OmniRoute gateway can route to (e.g. the NVIDIA omni model
  `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning` — BUT per providers.js:311-313
  the NVIDIA id must NOT be forced onto the OmniRoute base URL; use a gateway-valid
  vision model id). This prepends a guaranteed "seeing" model to the cloud chain
  (providers.js:316-318) so picture questions start from a vision model.
- Confirm `NVIDIA_API_KEY` is set (it is, per prior session) so the NVIDIA omni
  vision candidate is the FIRST attempt.
